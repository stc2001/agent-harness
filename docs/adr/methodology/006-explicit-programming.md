# ADR-006：显式编程原则 —— 框架层流程控制由确定性代码接管

**日期**：2026-05-13  
**状态**：已采纳  
**参考**：[MiniMax Agent Team 技术报告](https://agent.minimax.io/docs/techblog/agent-team) — "all driven by deterministic code rather than vibes"

## 上下文

Agent 框架的核心张力：哪些决策交给 LLM，哪些留给代码？

LLM 擅长语义判断（"这段代码做什么"、"这个结果合不合理"），但不擅长流程控制（"下一步跑哪个节点"、"何时暂停等用户"、"如何判断一个命令是否危险"）。后者需要的不是智能，而是确定性和可审计性。

## 决策

**框架层的流程控制、权限判断、状态流转全部由显式代码接管。LLM 只负责语义层面的内容生成。**

## 四条具体规则

### 规则 1：编排顺序 → 算法，不是 LLM

```
❌ LLM: "节点 B 和 C 都可以跑了，决定先跑哪个"
✅ Kahn 拓扑排序：编译时确定顺序，运行时不可变
```

见 ADR-001（Kahn vs LangGraph）。

### 规则 2：事件隔离 → 文件系统，不是上下文分辨

```
❌ 共享 session，靠 LLM 分辨"这条 tool_result 属于 B 还是 C"
✅ 每个节点独立子 session（独立的 events.jsonl），完成后合并到父 session
```

### 规则 3：权限判断 → 白名单，不是意图猜测

```
❌ 13 个 regex 猜"这个命令是不是在写文件"（2026-05-13 前）
   → perl -e 'unlink("/workspace/x")' 穿透
✅ 路径权限白名单：read_only 路径拒绝所有 sandbox_execute
   → 不猜意图，只看权限
```

### 规则 4：暂停点 → 显式 Gate，不是 LLM 自觉

```
❌ system prompt: "如果结果看起来有问题，请询问用户"
✅ DAGNode.human_gate = True / Phase.human_gate = True
   → 代码中的明确暂停点，不可跳过
```

## 本次审查中应用的实例

| 问题 | 显式编程修正 | 效果 |
|------|------------|------|
| `_is_write_command` 13 regex 猜写命令 | 删除。`read_only` 路径直接拒绝 | -22 行，零穿透可能 |
| `execute_task`/`run_loop` 50 行重复 | 提取 `_agent_loop` 单一实现 | -90 行，单一事实来源 |
| Coordinator Event 构造重复 8 处 | 提取 `_emit()` 辅助方法 | -50 行，一致的事件生成 |
| Orchestrator 取消检查重复 4 处 | 提取 `_check_cancelled()` | -30 行，取消逻辑集中 |

净减少 190 行，行为不变。

## 判断标准

遇到以下问题时，答案永远是**显式代码**而非 LLM：

| 问题类型 | 为什么不能交给 LLM |
|---------|------------------|
| "下一步做什么" | 编排顺序需要可审计、可重现 |
| "这个操作安全吗" | 安全判断不能有概率误差 |
| "应该暂停问用户吗" | 暂停点是实验协议的一部分 |
| "这段数据是谁产生的" | 数据归属需要确定性隔离 |

反之，这些问题仍然交给 LLM：

| 问题类型 | 为什么 LLM 合适 |
|---------|---------------|
| "这段代码实现了什么功能" | 语义理解 |
| "这两个结果是否一致" | 内容级别的验证 |
| "如何优化这段逻辑" | 生成式推理 |
| "用户需求可能遗漏了什么" | 对话和追问 |

## 后果

- 框架层代码量减少（消除重复和过度 regex）
- 安全边界更清晰（白名单替代黑名单）
- 重构阻力降低（单一职责 → 更容易提取 Scheduler/Executor/GateManager）
- 科学计算的可审计性增强（每一步流程控制都有明确的代码路径）
