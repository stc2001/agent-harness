# SOP：并发问题排查通用流程

> **来源**：docs/technical-report-parallel-toctou.md（并行 TOCTOU 问题排查）
> **适用范围**：多线程/多进程下的偶发 bug（flake、竞态、双执行、资源泄漏）
> **核心原则**：确定性优先 → 变量隔离 → 机制验证 → 闭环修复

---

## 0. 前置：判断问题类型

先回答三个问题，决定走哪条路径：

| 问题 | 特征 | 路径 |
|------|------|------|
| 能确定性复现 | 每次/高概率触发 | 直接走 Layer 2（变量隔离） |
| 偶发 flake | 单独跑过、全量跑挂，真实时序不稳定 | **先走 Layer 1（确定性复现）** |
| 资源泄漏 | 跑完后进程/文件/句柄残留 | 走 Layer 2 + 泄漏专项检查 |

---

## Layer 1：确定性复现

### 目标
把"偶发 flake"变成"必然失败"，锁定一个明确触发条件。

### 步骤（事件-目标-对象）

| 事件 | 目标 | 对象 |
|------|------|------|
| 真实时序无法稳定复现 | 构造可控触发条件 | 被测代码的依赖（stub/mock/backend） |

### 操作

1. 识别被测代码依赖的**外部不确定性**（真实进程、网络、时序、随机数）
2. 用 stub/mock 替换，注入**可控的不确定窗口**（如 `is_alive` 前 N 次返回 False）
3. 用并发工具（threading / multiprocessing / 高并发循环）放大触发概率

### 通过标准
- 同一测试**必然失败**，而非偶发
- stub 控制参数与失败行为存在清晰对应

### 代码模板

```python
class ControllableStub:
    """模拟真实依赖的可控延迟/失败窗口。"""
    def __init__(self, fail_window: int = 20):
        self.calls = 0
        self.fail_window = fail_window
    def is_alive(self, *a):
        self.calls += 1
        return self.calls > self.fail_window  # 前 N 次 "未就绪"

def test_concurrent_x():
    stub = ControllableStub(fail_window=15)
    # ... 并发调用被测代码 ...
    assert not stub.spawned_twice, "并发下不应双执行"
```

## Layer 2：变量隔离（对照实验）

### 目标
找出**唯一**触发条件，排除无关变量。

### 步骤

| 事件 | 目标 | 对象 |
|------|------|------|
| 复现成功但原因不明 | 逐变量隔离，定位触发条件 | 被测路径上的每个参数/标志/分支 |

### 操作

1. 列出所有可疑变量（标志位、参数、时序、并发度）
2. **每次只改一个变量**，其余固定，记录结果
3. 用**对照表**汇总：变量 × 结果
4. 关键组合用 **2×2 四象限**（如 锚点DWP × 探针DWP）定位交互效应

### 对照表模板

| 变量 A | 变量 B | 结果（存活率/通过率） |
|:---:|:---:|:---:|
| ✓ | ✓ | 1/10 |
| ✓ | ✗ | 3/10 |
| ✗ | ✓ | **10/10** ← 决定性 |
| ✗ | ✗ | 10/10 |

**读表法**：当某个变量从 ✓→✗ 时结果突变（10/10），该变量就是元凶。

### 通过标准
- 找到使结果突变的**唯一**变量
- 其他变量组合均不影响结果

## Layer 3：机制验证

### 目标
从"现象"下探到"机制"和"根因"，而非停留表象。

### 步骤

| 事件 | 目标 | 对象 |
|------|------|------|
| 已定位触发变量 | 解释"为什么它导致问题" | 底层机制（进程树/信号/内核行为/锁） |

### 操作（按可用性选择）

1. **进程/资源观测**：`/proc` 进程树、`wchan`、pgid/sid 关系、`ps --forest`
2. **信号追踪**：SIGCHLD handler 捕获子进程退出信号与状态
3. **系统调用层**：strace / 内核审计 / 追踪 kill/killpg/信号来源
4. **文档验证**：man page 的语义（如 bwrap `--die-with-parent` 的级联行为）
5. **对照验证**：临时移除/添加可疑标志，确认行为翻转（这是 Layer 2 的延伸，也是机制验证的一部分）

### 通过标准
- 能用机制**完整解释**现象（谁、在什么条件下、为什么）
- 机制解释能预测额外行为（如"去掉 DWP 会泄漏"被后续实验证实）

## Layer 4：闭环修复

### 目标
修复根因，且不引入副作用。

### 步骤

| 事件 | 目标 | 对象 |
|------|------|------|
| 根因确认 | 最小改动修复 + 回归 | 生产代码 + 测试 |

### 操作

1. **TDD**：先写确定性回归测试（Layer 1 的 stub 场景），确认 RED
2. **最小改动**：只改根因所在，不加多余抽象
3. **副作用审计**：修复后检查相邻行为是否被破坏：
   - 并发正确性（原 bug 不再现）
   - 资源清理（无泄漏——本例 DWP 移除后泄漏）
   - 接口契约（协议/签名是否被新依赖打破）
4. **全量回归** + 原 flake 测试多次运行确认稳定

### 通过标准
- 回归测试 GREEN
- 全量测试通过
- 无新泄漏/新 flake

## 泄漏专项检查

并发 bug 常伴随资源泄漏，修复后必须单独验证：

```bash
# 1. 记录基线
ps -eo pid,cmd | grep -c "<标志进程>"

# 2. 执行 N 次操作（spawn/kill 循环）

# 3. 对比增量
# 增量 = 0 为通过；>0 说明泄漏

# 注意: 用 pgrep -x <comm> 精确匹配, 避免 grep 自匹配
pgrep -x sleep | wc -l
```

**反模式**：`grep "pattern"` 会匹配自身。用 `grep "[p]attern"` 或 `pgrep -x`。

## 常见陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| 修现象不修根因 | 加等待/加延时"缓解" | 必须先机制验证 |
| 多变量同改 | 不知道哪个生效 | 一次只改一个 |
| 泄漏被忽略 | 修好主 bug，引入泄漏 | 闭环修复必须做泄漏专项 |
| 环境脏 | 残留进程干扰判断 | 每轮实验前清理环境 |
| 工具自匹配 | grep/ps 匹配到自己 | 用 `[x]` 技巧或 pgrep -x |

## 输出物

排查完成后应产出（对应本仓库实践）：
1. **技术报告**：`docs/technical-report-<issue>.md`（成功/失败路径 + 三元组步骤）
2. **ADR**：若涉及架构决策（如 `--die-with-parent` 语义变更）
3. **回归测试**：确定性测试进入测试套件
4. **SOP 沉淀**：可复用的排查流程
