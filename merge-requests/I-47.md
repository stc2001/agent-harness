## 变更摘要

让 py harness 能正确支撑**本地/自托管 OpenAI 兼容后端**（llama.cpp `llama-server`）。
三项缺陷在**云端路径下都不可见**（云端 tokenizer 与模型天然一致、无 thinking 模板差异），
换成本地小模型后才会静默出错。

**L1-01（正确性）**：`_count_tokens` 原先固定用 `tokenizer_dir/deepseek` 的 BPE，
而该词表**不含任何 CJK 字符** ⇒ 纯中文整段计入 **0 token**，`memory_summary` 折算
据此判定预算 ⇒ 中文语料预算形同虚设，真实 prompt 会冲破 `n_ctx` 被服务端 400。
改为**优先询问服务端自己的 tokenizer**（`POST <origin>/tokenize`，精确、离线、无需
tokenizer 文件），失败回退 HF；带结果 memo + 30s 负缓存（服务不可达时不逐次重试）。

**L1-02**：`_call_llm_once` 硬编码 `temperature=0.0`，`LLMConfig.temperature` 与
profile 的 `temperature:` 全部失效。新增 `temperature_override: float | None = None`，
`None` 时**保持上游贪心行为**（字节级不变）。

**L1-03**：推理模型模板 `enable_thinking` 默认 true，思维链吃光输出预算后返回
**空 `content`**（实测 `max_tokens` 16/64/256 全为空，512 才正常）。新增
`chat_template_kwargs: dict`，经 `extra_body` 透传，profile 可写 `enable_thinking: false`；
默认空 dict ⇒ 不改变既有请求形状。

### 必须处理

**R1｜L1-01「纯中文计数 > 0」由打桩满足，真实 HTTP 路径零覆盖（中）**

验收标准写的是「含『纯中文文本的计数 **> 0**』（当前 main 为 0，是回归防线）」。实际：

- 唯一断言 CJK `> 0` 的测试 `test_count_tokens_uses_server_result_over_fallback`，是先把 `_server_count_tokens` **打桩成 17** 再断言 17 —— 它验证的是**优先级**，不是修复本身；
- `test_cjk_is_zero_on_the_fallback_tokenizer_only` 断言的恰恰是 **CJK == 0**；
- **真实 `_server_count_tokens` 无任何测试**：URL 构造、POST、`{"tokens":[...]}` 解析、memo、30s 负缓存全部未覆盖（`grep` 确认全仓仅有的两处引用都是 monkeypatch）。
- 在无本地服务的环境（CI、本机）中文**仍计 0** —— 即该标准在此环境下并未达成（作者已在「评审须知」诚实披露，但披露≠达成）。

我独立验证了**实现是对的**（探针起了一个 mock HTTP server，`_count_tokens` 真的 POST 了 `/tokenize`、拿到 `tokens` 并返回计数）。所以请补一个走**真实路径**的测试即可：起一个 stub HTTP server（或 MockTransport）返回 `{"tokens":[...]}`，断言 CJK 计数 `> 0`。写法可直接参考 `.scratch/probe_i47_scope.py`（约 15 行）。

**R2｜`/tokenize` 端点跟随活动 profile ⇒ 云端 egress（中）**

issue「不在范围内」写的是**不改云端路径行为**，文档也把该机制描述为「**本机** `/tokenize`」。但 `_tokenize_url()` 的解析顺序是 `HARNESS_TOKENIZE_URL` → **活动 profile 的 base_url** → `http://127.0.0.1:8080/v1`，而 `_count_tokens` 是**无条件**先走服务端：

实测（`.scratch/probe_i47_scope.py`）：

```
[local profile]  derived URL -> http://127.0.0.1:<port>/tokenize
                 server saw  -> POST /tokenize  body={"content": "SENSITIVE PROMPT TEXT 中文机密"}
[cloud profile]  derived URL -> https://api.deepseek.com/tokenize      ← 指向云端
```

即：**云端部署下，`_count_tokens` 会把 prompt 原文 POST 到 `<cloud>/tokenize`**。后果：① 向未声明的端点发送 prompt 内容（该端点 404，随即进入 30s 负缓存并回退，故功能影响小，但 egress 是真实的）；② 若某服务商**确实**提供 `/tokenize`，计数口径会静默切到远端调用；③ 每 30s 一次注定失败的往返。

建议：默认**限制为 loopback**（或仅在显式配置/本地后端时启用），并同步修正 issue/文档里「本机」的措辞。

### 建议一并处理（低危）

**R3｜`HARNESS_TOKENIZE_URL` 语义不一致 + 一个名实不符的测试。**
profile 派生路径是 `origin + "/tokenize"`，而 env 覆盖值被**原样当作最终端点**（不追加 `/tokenize`）。`test_tokenize_url_is_origin_not_v1` 的名字与 docstring 说「llama.cpp 在 ORIGIN 提供 `/tokenize`，POST `/v1/tokenize` 会 404」，但它断言的却是**原样返回含 `/v1` 的值** —— 若用户按「base_url」语义设置该变量，POST 会打到 `/v1`，正是该 docstring 自己说会 404 的形态。建议统一语义（要么统一按 base_url 处理，要么改名为 `HARNESS_TOKENIZE_ENDPOINT`）并修正测试名。

**R4｜`_TOKEN_COUNT_CACHE` 无上限、无淘汰。**
键是 `(url, 原文)`，全文件仅有 `.get()` 与 `[]=`，无 LRU/容量/清理（已 grep 确认）。注释自述「一轮 ~43 次计数、约 199k 字符」——这些**原文会被永久驻留**，长驻进程下构成与历史文本量成正比的内存增长。建议加容量上限或只缓存文本长度而非原文。

**R5｜超时值与注释矛盾。**
`urlopen(req, timeout=20)` 上方的注释是「Short timeout: a count must never stall a turn」，但 20s 并不短：服务**接受连接却不响应**时，单次计数会卡 20s（负缓存只在**失败之后**才生效）。建议降到 1–2s，或把注释改成实际语义。

### 结论

三项缺陷的**实现本身经复验成立**（L1-02/L1-03 我使用了比作者更强的 wire 层验证，L1-01 的真实 HTTP 路径也由我实跑确认可用），回归干净、无既有测试被削弱。因此**不需改动功能逻辑**即可解决 R1（补测试）与 R3–R5（文档/小修）；R2 需要一行「仅 loopback」的门控。

运行时零影响，故不阻塞合并；但留着有实际风险：后来者若照该句把代码「改对」，就会**重新打开 prompt 外发**。已一并纳入 **I-48**。
